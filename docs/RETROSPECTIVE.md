# Retrospective — StudySprint

Going into this capstone, my plan was fairly linear: build the core CRUD features, add the dashboard, then test and deploy. In practice, deployment turned out to be the hardest and most time-consuming part of the whole project — not writing the application code itself. I underestimated how much of "shipping" is actually about environment configuration, dependency management, and tooling quirks rather than features.

The biggest failure I ran into was the Railway deployment. My first two attempts both failed for different reasons — Railway's auto-detection (Railpack) couldn't handle my project's two-`package.json` structure (separate `client/` and `server/` folders), and every workaround I tried to patch around that (custom build commands, changing the root directory) broke in a new way. I eventually had to step back and switch to a Dockerfile instead of continuing to fight the auto-detected build system, which gave me full control and worked on the first real attempt. Even after that, the app crashed in production because my Dockerfile used an older Node version that didn't support a built-in module (`node:sqlite`) my code depended on — an environment mismatch I hadn't thought to check.

If I did this again, I'd verify my exact local Node version and pin it in the Dockerfile from the very start, instead of discovering the mismatch through a production crash. I'd also run `npm audit` earlier and more incrementally, rather than doing one large audit pass at the end — that would have caught the dependency issues in smaller, easier-to-diagnose batches.

What I'm most proud of is not giving up on the deployment step after the first two failures, and instead diagnosing each error message carefully enough to figure out the real root cause rather than guessing. The most important thing I learned is that "it works on my machine" is a genuinely different problem from "it works in production," and closing that gap is its own skill separate from writing application code.
